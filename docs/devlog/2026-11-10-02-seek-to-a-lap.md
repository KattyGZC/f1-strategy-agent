# 2026-11-10 · 02. Seek to a lap

**Goal:** a viewer types a lap, and the replay screen rebuilds as it was at that lap's earliest start, then plays on.

## What happened

1. The author asked for the next step on the project; the agent named seeking to a lap, the last PR of phase 3 (ADR 0009), and planned it. The author chose a number field with a button and seeking in every session, qualifying included.
2. Built on `feat/seek-lap` by layer, with [ADR 0012](../adr/0012-seek-to-a-lap.md). Phase 3 is done in `AGENTS.md`.

## Decisions

- **A seek replaces the stream with a new generation**, so a replay's memory stays bounded; producers run until their replay is gone; appends are capped by `REPLAY_APPEND_BATCH`; a failed replay cannot be sought: [ADR 0012](../adr/0012-seek-to-a-lap.md).

## Corrections and redirections

- The agent's plan let the producer end at the timeline's end and had the seek start one again. While writing it the agent found a seek racing a finishing producer would be lost, and made the producer keep ticking instead.
- The plan made the append cap conditional on a measurement over 50 ms. The measurement gave 91 to 126 ms, so the cap went in.
- A `hypothesis` property failed on a 1e-280 s offset; the agent restated it on the microsecond grid that timestamptz instants live on.
- Mutation testing found an equivalent mutant in the lap-start rule; the agent rewrote it with `min` instead of excluding it.
- The fresh-eyes audit returned ACCEPT-WITH-FIXES (a 63-line `watchReplay`, a failed replay that could be sought, return codes defined twice); fixed, then SHIP.
- Measured in the browser, a seek to lap 57 shows after about 9 s: Chromium's EventSource takes 6.7 s for the 31,701 catch-up events, against 1.3 s with curl. The agent offered to compact the catch-up; the author chose to ship as is and open an issue.
